## Deployment and launch boundary

A is first: qualified lockdown under the donor's own user, no administrator rights and no separate UID, sandbox or egress guarantee. If the harness is compromised, it can act as that user. B follows with two identities, one administrator request, per-UID egress and a kernel read boundary; its 0600 bridge-owned keys use no Keychain, and B stays disabled while its separate provisioner contract is pending. C is the sandbox fallback under the donor UID when administrator rights are declined or unavailable. A/C use Secure Enclave P-256 signing/SSH keys on qualified Macs that support them, 0600 files elsewhere; package-decryption keys are separate X25519 keys. Algorithms and storage must be qualified for the selected tuple.

Only the human donor initializes. Interactive TTY, typed consent and managed-session environment checks are policy admission heuristics, not proof of human identity. The bridge accepts only `lockdown` + `remote-auto` with an exact qualified build and current policy generation. Qualification requirements are not evidence that a tuple passed. The supervisor consumes a caller-composed plan; it does not compose one. The relay owns no keys or network; it forwards local MCP calls. Tools execute in the project workplace over one donor-originated SSH connection; the project never connects back to execute on the donor. Every donor variant, including A and read-only access, requires the project-side `workplace` account class, helper v1 qualified zero egress (including denied loopback, no proxy destination), R-EXEC and the R-CEILINGS capability matrix with published applied state at activation; one-host slice 0 alone is insufficient. The fixed root-owned login shell/forced-command stub only relays to service-principal `swarma-rb-exec`, reads no user startup files and accepts only sshd's forced-command invocation. The service authenticates kernel peer UID and active generation. Tool policy/caps, claims/floors, output cache, audit and mailbox controls remain outside workplace write/signal authority. Jobs use dispatcher-owned starts through the root launcher/start receipt and journaled `exec.stop`; process-group death alone never establishes descendant absence. Broker/dispatcher/host Unix sockets refuse a workplace without a configured role; R-SOCKETS also qualifies the complete reachable socket set against the declared platform set. R-SHARED keeps shared ingress/message/media/operator-session services off hosts admitting the untrusted class; the join entry host is separate.

## Trust and SSH

Web PKI validates the join domain. DNSSEC is the default and is validated inside the client from an embedded root anchor; DoH is a transport fallback when system DNS strips signatures, not a different trust source. Closed networks may supply a zone anchor. Records are per environment: `TXT _swarma.<domain>` for root fingerprint, `TXT _swarma-ssh-ca.<domain>` for SSH host CA public key, and join-point `TLSA`.

Invitation pins select the fallback only when the invitation explicitly declares an environment without a DNSSEC domain. When DNS and invitation pins coexist they must agree. Mismatch, malformed/failed reads, bogus or unresolved validation refuse; they never become evidence of absence or activate fallback. Open applications without invitation pins require DNSSEC. No second human channel is used.

The host CA (Ed25519, kept in the keeper or hardware token) certifies host keys; the donor uses `@cert-authority` and verifies host name, validity and KRL on every connection. Host certificates of about a year are policy examples. Adding a certified host changes no DNS record; CA rotation overlaps the old/new keys. A separate user CA certifies donor-generated `K_ssh` with the workplace-user principal, with certificates of about a day as a policy example. The private user CA key is held by the project key keeper or a hardware token outside the workplace UID. The donor bridge requests renewal through service-principal authentication; the signing service issues only the authenticated active workplace's principal under current admission/revocation. Renewal formats are unpublished. Root-controlled sshd trusts `TrustedUserCAKeys`, checks revocation and enforces the protected absolute relay-only forced command and fixed no-startup-file shell with no forwarding, PTY, user rc or environment. Retirement/revocation stops renewal, updates user-certificate KRL and closes established sessions; revocation alone does not terminate an existing connection.

## Join service and limits

The join point sits on the project's public entry host behind existing TLS ingress, under its own name. It holds no admission-signing key and executes no command: it challenges, stores signed enrolment/application data and returns operator-signed encrypted packages after admission. Invited enrolment uses a random one-use code of at least 128 bits, challenge-bound signature, atomic consumption and replay tombstone. Same-key retries recover the same pending enrolment; other-key retries refuse. Open applications have no invitation code and enter the same operator queue; exact schema is pending.

D9 owner-approved policy values are 10 requests/minute and 100/day per source address, five challenges per invitation, one use, 72-hour invitation validity, 16 KiB maximum request body, five-minute challenge lifetime and 50 pending applications. New applications beyond the pending cap refuse until capacity is available. These values do not substitute for the pending API/error schemas or imply a published cleanup/polling format.

## Tools, mailbox and lifecycle

The effective tool set is the relay maximum intersected with workplace policy. Mailbox operations are control plane and appear as tools only when granted. Donor admission checks verification records, binding, expiry, fences/revocations and delivery mode before a session-input adapter receives a turn. Cursors advance after persistence; message IDs deduplicate; the application receipt is separate from transport acknowledgement. A dropped channel pauses new turns; a current turn reaches its deadline, calls fail `channel_down`, and outbound results queue durably. Reconnect checks SSH certificates and reconciles the original durable effect identity, argument digest and admission window. The ten-minute output cache is separate from replay evidence; its expiry never authorizes repetition.

### Remote effect claims and recovery (F-7)

At the service-principal workplace effect owner outside the workplace UID, durably claim each binding-generation-scoped operation identity, operation and canonical-argument digest before mutation. This covers tool effects such as `exec`, `file.write` and `patch.apply`; signed mailbox claims do not automatically cover them. Same-identity retries retain the original arguments and admission window; operation/argument mismatches refuse. A known claim without a conclusive result stays `pending` or `unknown_result`, never automatically re-executed. Cached output lasts ten minutes and may be returned while retained; a cache miss proves no absence.

Authenticate new-versus-retry admission with a bounded sequence or epoch floor. New work must fall within the current admission window; an unseen expired identity refuses. Output expiry does not grant a retry a fresh window. Persist floor advancement before discarding claims, and discard claims only after their identities can never be admitted again. Indefinite bindings must allow bounded claim storage without losing replay safety. A new identity requires an explicit new-effect decision.

Reconcile durable claims and admission floors before recovery opens admission. Lost, restored, unreadable or contradictory evidence keeps the binding closed. Reuse R-OBS states where applicable: `recorded` with recorded result and current target state, `pending`, `rolled_back`, `not_recorded`, `unavailable`, `contradictory`. Only complete authoritative evidence establishes `not_recorded`; missing/expired/unreadable evidence is `unavailable`. Reads are authenticated to the original caller principal or operators, scoped to the original effect identity, operation and argument digest, and serialized with the receiver journal. Observing absence or rollback never authorizes an automatic new effect. No service or exactly-once completion guarantee is added.

**Open publication entry — remote claims/admission:** would need canonical argument bytes/digest rules, binding-generation identity encoding, authenticated new-versus-retry encoding, selected bounded sequence/epoch floor, durable claim/floor retention and recovery order, R-OBS response encoding, exact refusal codes and negative vectors. These remain part of the unpublished channel/backend formats. No new wire field, code or policy duration is specified. Qualification would need lost reply/long disconnect/cache expiry, mismatching arguments, new versus stale admission, concurrent retries, receiver crashes around claim/mutation/result persistence, claim-store rollback/loss and interrupted reconciliation; see the CIP-0009 test plan.

The donor bridge signs final envelope bytes with `K_sig`. The project verifies signature/grants/freshness and carries those bytes unchanged under a distinct audited carrier authority in the first slice. No project carrier credential enters the donor package. Later organisation accounts and allowlisted freelancer federation are a separate rollout phase.

Track donor installation, donor execution, project workplace and signing identity separately (CIP-0009 D7). Local stop persists before termination and keeps bridge/keys; leave keeps identity for a new admitted workplace; purge removes only variant-owned artifacts and can happen offline. A/C never remove the donor account. B cleanup belongs to its pending separate provisioner. Project suspend/retire/revoke are independent: retirement closes sessions and journal-stops workplace executions through `exec.stop`, revokes channel/grants/user certificates, after confirmed account-wide process absence and a write fence, records R-TRANSFER export or explicit operator waiver, performs declared-key cleanup, deletes the workplace home and releases the account; retirement metadata alone is service-generated closed-schema data without agent-controlled strings, names, links or bodies; this does not restrict the separate bounded code change set. Keeping a home is a separate explicit operator operation stating that confidentiality is not guaranteed; git/accepted outputs retain their separate policy. After ordinary retirement, the donor identity remains pinned. Only a separate operator-authorized signed revocation revokes that identity; the one-shot dispatcher exception does not apply. Offline purge reports remote revocation as unknown.

The OS writable boundary is the UID's writable set; task write scope is plan-bound and import-enforced. R-NET-TOOL requires zero egress with no proxy and denied loopback. Standalone private Git administration crosses accounts; same-account worktrees stay. No new wire field or refusal code is allocated.

## R-TRANSFER: code as data, then exact candidate

The only path is CIP-0009 D5a's eight-step round: **materialize, work, round end, export, candidate, review, rework, integration**. The caller supplies admitted repository commit B's bounded canonical tree archive; the dispatcher relays/journals it and holds no repository. `swarma-workspace-materialize` writes a fresh standalone private repository under the child UID, no remotes/hooks/credential helpers. The plan digest binds B, canonical manifest digest (path → supported Git kind/mode and content identity, derived from immutable B objects), task write scope and exec profile. Validators stay outside write scope unless the task is about them; dependencies are platform-seeded read-only caches. Before work, verify every archive entry against the immutable manifest, refusing content/mode mismatch and missing/extra entries; preserve immutable exporter access. Original workspace admission consents to bounded cleanup collection after ordinary expiry, tied to generation/round/exporter/base/manifest/scope, never worker or successor authority. Worker Git history is never imported. The worker has no network, push or merge-request access.

A remote signed final envelope (local board outcome) ends the round. Account-wide confirmed absence and a workplace write fence precede `swarma-workspace-export` under the child UID with fixed environment/no network. It walks without following links, skips Git administration and emits only changed regular-file content/executable bit, symlink text and deletions against both manifest kind/mode and content identity; mode-only edits and equal-blob regular↔symlink swaps are modifications, and deletion reports the prior mode. File-count/per-file/total/binary caps are unpublished. RWP v2.1 §8/§10 gates are adopted: special files, `.git` path components however spelled, case-fold/Unicode-normalisation collisions, gitlinks/submodules, root escapes and exceeded caps refuse the whole export. No partial output. Dispatcher records verified durable custody of the result and every referenced blob outside the home/deletion path; metadata alone or incomplete content retains the obligation. Retain content with bounded accounting until authenticated import acknowledgement or another explicit authorized release. Result retrieval requires current authority of the original caller; the board accepts it as a resource. Export cleanup obligation blocks home deletion until recorded export or an explicit operator waiver. An intermediate turn-boundary export uses the same fence/absence requirements. Recorded export, immutable deterministic refusal, interrupted/unknown export and authorized discard remain distinct. Refusal retains the obligation and yields no C; same-workspace repair requires current authority, separately admitted plan-bounded turns and new linked execution/export effects, with write/SSH fences closed through each export. Budget exhaustion requires a per-act content-confirmed operator waiver; automatic standing discard remains unchosen and off. Source-entry permission failure needs producer-published classification/typed failure; infrastructure denial and I/O/storage uncertainty cannot be policy refusal. Never mutate permissions or increase exporter privilege. Physical materialize/work/export launches have distinct existing claims/effects/receipts and confirmed absence; ambiguous starts reconcile without duplication. Bounded cleanup capacity obeys accounting and security holds; expired work authority grants no repair, and revocation/compromise/ALLSTOP/maintenance/restore cannot be bypassed. Never launch a retiring generation or reuse worker/R-SESSION evidence. See [CIP-0009 D5a](../cips/CIP-0009-donor-side-deployment-and-bridge.md#recommendation) for publication and qualification cases.

Import recomputes the canonical manifest independently from immutable repository B using the same encoding, refusing unless the result’s `base_commit` equals B and its `manifest_digest` equals the recomputed digest, while retaining result-to-admission checks. The orchestrator's deterministic board import builds on B in a scratch index, hooks disabled and no attribute filters/drivers. Hard refusals are `.git` components, outside-write-scope paths and `.task-board/` changes. Flagged paths are CI (`.github/**`, `.gitlab-ci.yml`, `.circleci/**`), Git behaviour (`.gitattributes`, `.gitmodules`), hooks/auto-run (`.githooks/**`, `.husky/**`, `.pre-commit-config.yaml`, `lefthook.yml`, `.envrc`, `.vscode/**`), agent instructions/configuration (`AGENTS.md`, `CLAUDE.md` anywhere, `.claude/**`, `.codex/**`, `.agents/**`, `.mcp.json`) and all symlinks. C is signed by repository identity, with worker/run/result-digest trailers; its tree equals independent recomputation from B plus change set. The board keeps one trusted integration baseline for the candidate series, separate from materialization base B, and recomputes C's complete review delta and sensitive-hunk set against it, including retained changes from unaccepted candidates. Fully reverted sensitive content need not remain flagged. Baseline and complete flagged set bind to C's exact OID. The independently approved harness H remains a separate verification-control revision, not the integration review baseline.

A trusted reviewer, neither untrusted-class nor producer identity, reviews exactly C. K1 acceptance never transfers by patch equality; every sensitive hunk in the integration-baseline report needs fresh explicit acknowledgement bound to the exact candidate OID, with no previous verdict or acknowledgement carry-over. Unresolved web provenance inherited from unaccepted candidates is a separate candidate-level obligation, surfaced from ancestry and recorded provenance and bounded at that baseline; it never changes the current run's factual capability class. Clearance requires a published conservative provenance/removal rule or explicit exact-candidate reviewer resolution; editing/rewording alone proves no removal of the dependency. Accepted baseline content need not propagate it indefinitely, and acknowledgement does not make incomplete provenance complete. All required provenance acknowledgements and reviewer resolutions also bind to the exact candidate OID and its fresh verdict. All candidate execution uses R-VERIFY; untrusted candidates are never pushed before acceptance where CI would run with secrets. Changes requested record findings and send a signed task letter with C as the next admitted base; the donor session continues, the workplace is freshly materialized, old workspace removed only after recorded complete-content custody or explicit operator waiver, and C2 builds on C while retaining the trusted integration baseline. Recompute the full C2 sensitive/provenance obligation set and obtain fresh exact-C2 acknowledgements and verdict. Local rework is a new run with findings. Questions use ordinary letters/outcomes. Accepted exact head integrates only by board signed fast-forward K1/K3; a moved base or changed trusted integration baseline requires ordinary refresh/re-review. RWP exporter ownership differs only in using an approved child-UID executor rather than the harness/container-volume reader.

## R-NET-TOOL, R-EXEC and R-VERIFY

Workplaces have zero egress and denied loopback, no proxy destination: Linux qualified per-execution namespace without external interfaces plus Unix-socket-only address families; macOS qualified network-denying sandbox and per-UID deny. Platform hosts bind neither `direct` nor `external-http-proxy` to any account; operator machines without the platform retain those/cooperative profiles. Local trusted agents use provider endpoints through bound profile proxies; one listener per generation, own port, allowlists/no mail ports, private/metadata dial guard, attributable caps/logs belong to N15, not this wire protocol. Runner dependency egress follows the same proxy requirements.

Default donor loop reaches only model-provider endpoints and our host; no search/fetch tool or donor-side web server, no internet in the project environment. CIP-0008 lockdown plan alone disables provider-side search inside the provider API, invisible to network rules. Outside web content mixes contexts and invites injection. Tasks instead carry trusted-side checked resources as board resources and signed-task-letter attachments, read-only next to the workspace with plan digests; data, never instructions. More resources are requested by letter/outcome; the worker never fetches.

An operator act at admission may admit a remote worker to the trusted circle for per-identity donor-side web opt-in only, never the untrusted class. Options remain pending qualification: provider-side search under a new CIP-0008 tuple proving provider execution/no local fetch, or platform-shipped donor MCP `swarma-web`. The latter uses its own B identity or C sandbox, never harness/bridge identity; egress is search-provider API endpoints only, never arbitrary fetch. It holds the donor's own key there (A: donor Keychain or 0600 file), donor consent at `init`; no key crosses channel/frames/packages, and no project method requests it. Results reach only the donor model. The harness keeps provider-only egress; other lockdown controls stay.

R-EXEC is an OS executable allowlist per task class, with non-executable writable areas. Excluded for all agent classes: compilers/linkers/transpilers/bundlers, test runners, package managers/installers, containers/VMs, network tools and harness/agent binaries. Editing, local Git inspection/search and qualified light type checks are admitted by profile. Shared light/heavy executables need a D-PATH protected fixed-subcommand wrapper proving heavy forms refuse; interpreters only as needed, bounded by ceilings. Qualify executable, protected entrypoint/arguments, environment and all transitive code/configuration inputs: worker scripts, inline evaluation, imports, plugins, startup files and executable configuration must not execute locally. Prove protected/disabled or pinned loading and direct/indirect heavy-form bypass refusal through the actual tool path, with inert positive controls. Fixed subcommands, wrapper ownership and non-executable mounts alone are insufficient; an unqualified tool uses R-VERIFY. No account starts its own loop/environment. All heavy work and all worker-code execution use R-VERIFY secret-free isolated ephemeral runners on another machine with controlled dependency egress; downloads only there. Tester orchestrates and reads board data in testing state, never executes candidate code. `agent-headless-build` is withdrawn for agent accounts.
