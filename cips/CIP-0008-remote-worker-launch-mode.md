## Revision 2: what the architecture review changed

The first draft was reviewed on 2026-10-08 (research task, read-only, 25 findings). This revision folds in every finding that concerns this CIP; the finding numbers (F1–F25) refer to that review and are kept in the text so the owners can trace each change.

- **F1:** the launcher no longer refuses "any R4 argument in a lockdown plan" (which would refuse the very flags the composer emits). It distinguishes the **generated policy** (what agents-management spells) from the **caller tail** (what the caller adds after `--`), parses the tail against a closed, versioned per-harness grammar, and validates the fully expanded argv, configuration and plugin contribution against the canonical generated policy at intake (R4, R5).
- **F2:** the Codex row ships only the **measured app-server path** of `rwh` (the whole recipe: sanitized catalog, every feature switch, root `web_search = "disabled"`, no request-user-input, analytics off), not a partial `exec` recipe; the dispatch tripwire is detection after dispatch, and a missing tool-surface audit is a refusal, not an empty safe surface (R3).
- **F3:** Claude's `--restricted` ignores user, project and local settings but keeps vendor managed policy and an explicit `--settings`; the Curator-written settings file is therefore passed **explicitly** as a protected file, hooks/plugins/sync/instruction discovery/skill execution are disabled and measured separately, the OAuth-token launch is qualified without `--bare`, and the print-mode and interactive branches are distinct vectors (R3).
- **F4:** Muse keeps its session logs (its continuity and usage accounting depend on them); budgets that matter are counted on the trusted side (R3, CIP-0009 D1).
- **F5:** rows pin an exact **qualified tuple** (executable digest, release, platform, transport, model/catalog, settings policy, sandbox revision); an update is a requalification; the banner promises what is true (R3, R6).
- **F6:** posture and permissions travel as Decision 0013 §6.4 **plan extensions marked required**, in a plan revision that old readers refuse precisely; the v4 schema changes of CIP-0002/0003/0006/0008/0010 are coordinated in one table (R5, §Schema coordination).
- **F7:** environments §12.2 is amended explicitly so that a lock may pin the pair `lockdown` + `remote-auto`; locks still never select credential material (R1, R2; CIP-0010 C3).
- **F8:** no second flag compiler and no `--mode remote-worker`: agents-management composes through the one construction site, the remote-worker supervisor **consumes** a composed plan (Decision 0019/0021 amendment named in §Specification changes), and posture is a target/posture field independent of the interaction mode (R5, §Compatibility).
- **F9:** plan immutability is not policy freshness: the plan binds a **policy generation**, and the executor rechecks the current generation at exec and at resume; a changed machine configuration invalidates plans and stops active sessions at a defined point (R5).
- **F17:** `stop`, `leave` and `purge` are separate transitions; this CIP no longer says that a donor command deletes a carrier identity the donor never holds (R6; CIP-0009 D7).
- **F22:** the credential claim is honest: a token delivered in the process environment is readable by the harness; that is the owner-approved trusted-process posture of the first release, not non-extraction (§Security).
- **F25:** the acceptance evidence is spelled out: the visible tool set is measured against the permitted set, and unknown audit coverage, unknown releases, a failed settings read or missing sandbox support refuse (R7, §Test plan).

## Summary

A **remote worker** is a harness whose model runs on a machine we do not own (the *donor*'s machine) while every tool call executes inside a remote workplace on our host. This CIP adds a launch posture in which the harness starts with **no locally acting tool offered to the model**: the only tools are the remote-tools relay (CIP-0009) and, through it, the mailbox. The lockdown is a machine-level **tool posture** bound to a profile, compiled per harness by agents-management from a qualified tuple, enforced by the launcher (a closed caller-tail grammar and an intake check of the expanded launch against the generated policy), bound to a policy generation that the executor rechecks at exec and resume, recorded in the plan, the receipt and `env status`, and visible and stoppable by the donor. Permission prompts are answered by a distinct policy, `remote-auto`, that pre-approves only the admitted remote tools and denies everything else without prompting; it is never a native bypass. The design reuses what `rwh` already measured for Claude, Codex and Muse and moves it from a hand-written harness into Curator's declared surfaces. What this CIP does *not* claim is in R8: the enforced boundary on the donor is the OS confinement of CIP-0009, not a launch flag.

## Motivation and user stories

- **Owner (2026-10-08):** "the native tools of the remote harness are switched off or overridden at launch, so a compromised or prompt-injected environment cannot act on its own machine; the donor must be able to see it and control it."
- **The donor** lends a subscription and a machine. They want one command that provisions the thing, a visible posture ("this harness can only talk to our project's workplace"), an audit of what left their machine, and a kill switch that does not depend on us.
- **The project orchestrator** wants the same pin and plan discipline as for local workers: the remote executor accepts only a plan whose profile pin, posture and policy generation match, and a harness that could act locally is never admitted (VISION v1.3 LCH §8).
- **The platform** wants this to be a Curator posture, not a bespoke launcher: one composer, one plan schema, one refusal table, one place that owns the native grammar (Decision 0019).

## Current state

- **No deny field in a profile.** A profile carries skills, instructions, the MCP set and context (environments §2, §3, §9, §10). Native settings files (Claude `settings.json` `permissions.deny`, hooks) are outside the managed surface: Decision 0014 is still *proposed*; CIP-0006 (Draft) covers preserving legacy provider settings and MCP opt-outs, not tool denial.
- **The only permission knob is `permissions.<profile>` with values `native|yolo`** (Decision 0018; environments §12.1). `yolo` maps to Claude `--dangerously-skip-permissions` and Codex `--dangerously-bypass-approvals-and-sandbox`; `pi` refuses it. There is no restricted or lockdown value. In `native` mode argv after `--` is forwarded verbatim (0018 item 4), so a caller *can* pass `-- --disallowedTools Bash,Edit,Write`, but 0018 says plainly that this interface is UX, not a security perimeter, and it is not a profile property. Environments §12.2 permits a `permissions` lock only toward `native`.
- **MCP injection is partial** (CIP-0002 §Current state): Claude's `--strict-mcp-config` is applied only when the profile's MCP set is non-empty; Codex seed revision A inherits native MCP servers (fixed by seed revision B, landing for v0.15.0-rc.5); an `http` MCP declaration carries no per-profile authentication (environments §2.2). Current Curator records older verified harness releases in its registry and has no Muse MCP adapter row.
- **`rwh` already runs locked-down remote harnesses on the dedicated Mac mini** (relux-works/remote-worker-harness, modes 2b Claude, 2c Muse, Codex session; live-accepted 2026-09-29 and 2026-10-06). Its measured per-harness recipes are the evidence base of the mapping table below, *for the releases and modes it states*. Two of its assumptions matter here: it isolates native discovery with a scratch `HOME` (a Curator launch preserves `HOME`, so the native-source inventory has to be rebuilt for the dedicated donor account), and its Codex path is the **app-server** with thread-level dynamic tools, not `codex exec`. What `rwh` lacks is exactly what this CIP adds: a declared posture, a plan that covers it, a launcher grammar and a donor-facing control surface.

## Design

### Options considered

1. **Profile bytes carry a tool deny list.** Simple to author. Violates environments §10.3 ("a profile chooses what the context says, never how a process is launched") and makes a security property depend on package bytes that any overlay could change. Rejected.
2. **Per-launch native arguments only (today's passthrough).** Works, as `rwh` shows, but nothing records the posture, the plan does not cover it, nothing refuses the opposite arguments, and a donor cannot lock it. Rejected as the end state; kept as the mechanism the mapping table compiles to.
3. **A machine-level tool posture bound to a profile, compiled per harness by agents-management, enforced and refused by the launcher, bound to a policy generation, recorded in plan and receipt.** The same shape as Decision 0018's `permissions.<profile>`; lockable by the donor's system configuration; the profile contributes only what it may (the remote-tools MCP declaration and the instructions). **Recommended.**
4. **Ship a separate "remote worker" harness wrapper.** This is `rwh` today. It duplicates the composer and spells flags outside Curator; the owner asked for a Curator mode.

### Recommendation

**R1. Posture knob and lock.** A new environments §12.1 knob `tool_posture.<profile>` with the closed values `open` (default, absent) and `lockdown`. It is a *machine* knob: lockable by system configuration (manager §12), never profile content, never a launcher-file entry. The donor's installation locks `tool_posture.remote-worker: lockdown` (CIP-0009), so no launch of that profile on that machine can be `open`. **Lock amendment (F7):** environments §12.2 today permits a `permissions` lock only toward `native`; this CIP amends it so that a lock may also pin the **pair** `tool_posture = lockdown` with `permissions = remote-auto` (and nothing else: a lock toward `yolo` stays refused). The §12.2 rule that a lock never selects or constrains credential material is unchanged; CIP-0010 keeps the credential source in the user-owned layer.

**R2. Permissions value for the posture.** Decision 0018's `permissions` gains a third value `remote-auto`, admitted **only** when the effective `tool_posture` is `lockdown`; `remote-auto` with `open`, or `yolo` with `lockdown`, is a `usage` refusal naming both. `remote-auto` means: the tools of the admitted remote-tools server are pre-approved, everything else that would prompt is denied without prompting, and **no native bypass is requested in any source** (a bypass spelling found in the generated policy, the caller tail, a settings file or a configuration key is a refusal). It is a distinct permission policy with two qualified spellings per harness, one for the print/headless branch and one for the interactive branch, each with its own conformance vector (F3). This is the "marked yolo" of the owner brief.

**R3. Compile per harness in agents-management** (the Decision 0018 owner of provider mappings; goldens per **qualified tuple**). A qualified tuple is `{harness, release, executable digest, platform, transport, model or catalog digest, settings-policy digest, sandbox-profile revision}`; a row applies to exactly that tuple, an update of any member is a requalification, and a tuple without a row refuses (`tool_posture_unsupported`). **R4. Launcher grammar (F1).** Under `lockdown` the launcher separates two inputs:
- the **generated policy** of the row (R3), which is required: a plan whose expanded argv, configuration files, environment or plugin set lacks a required member, duplicates it, spells an alias of it or supplies the same setting from another source is refused at intake with `launch_plan_invalid`;
- the **caller tail** (arguments after `--`), parsed before any process exists against a closed, versioned per-harness allowlist. First revision: Claude `--output-format`, `--verbose`, `--resume <id>`, `--session-id <id>`, `--max-turns <n>`; Codex app-server: none; Muse: `--resume <id>`. Every other option refuses: `tool_posture_conflict` (usage, exit 2) for a known re-enabler (for example Claude `--tools`, `--allowedTools`, `--disallowedTools`, `--permission-mode`, `--dangerously-skip-permissions`, `--add-dir`, `--mcp-config`, `--settings`, `--setting-sources`, `--plugin-dir`, `--plugin-url`, `--bare`, `--remote-control`, `--agents`, `--worktree`, `--tmux`, `--brief`, prompt-file options; Codex `-s`, `-a`, `--approve-for-me`, any `--dangerously-bypass-*`, `--add-dir`, `--enable`, `--disable`, `--search`, `--remote`, `-C`, `-p`, `--worktree`, image and output-file options, any `-c`; Muse `--enable-shell-tool`, `--disable-sandbox`, `--sandbox-network`, `--yolo`, `--disable-approval`, `--trust-workspace`, `--approval-mode`, `--approval-judge`, `--permission-profile`, `--workspace`, `--worktree`, `--image`, `--prompt-file`, `--base-url`, `--agents`), and `tool_posture_unknown_argument` for anything not in the allowlist, in `=` and separate forms. An unknown harness or an unknown tuple fails closed (`tool_posture_unsupported`): a failed probe is not known support, as in 0018 item 4.

**R5. What the pin, the plan and the policy generation cover.**
- The profile **pin** keeps covering the lock: the remote-tools MCP declaration package (environments §2.2, with the canonical source identity of CIP-0009 D3) and the instructions. Posture is not profile content and never enters the pin.
- The **plan** carries two Decision 0013 §6.4 extensions, `works.relux.curator.tool-posture/1` (`open|lockdown`, the qualified tuple identifier, the sandbox-profile revision) and `works.relux.curator.permissions/1` (`native|yolo|remote-auto`), both listed in a new outer member `required_extensions` of a plan revision; an intake that does not implement a required extension refuses `launch_plan_unsupported_extension` (F6: an old reader that ignored the extension would launch open, so ignoring is not an option). The receipt and `env status` print both.
- The **policy generation** (F9): the machine configuration keeps a monotonically increasing `policy_generation` (counter plus digest of the locked members). The composer copies it into the plan; the **final executor** reads the current generation from the trusted policy store at exec and at every resume and refuses `policy_generation_stale` on mismatch; the supervisor stops an active session at the next turn boundary when the generation changes, immediately when the change concerns `tool_posture` or `permissions`. On the donor the trusted store is the bridge identity's configuration (CIP-0009 D1), not a file the harness can reach.
- The remote executor compares `expect_pin`, `tool_posture = lockdown`, the policy generation and the tuple before intake and refuses otherwise (VISION LCH §8). Its acceptance record names the backend and the boot qualification it actually has; a donor supervisor's assertion is recorded as an assertion, never as attestation of the donor's kernel state (F9).

**R6. Donor visibility and control.**
- *See:* `curator env status` on the donor machine shows, per managed home, `tool posture: lockdown (tuple <id>, policy generation <n>)`, `permissions: remote-auto (no local tool is offered to the model; the harness runtime keeps its own managed state; tools execute in the project's remote workplace)`, the remote-tools server identity and the project it is bound to. The same sentence is the harness's banner at session start and the `remote-auto` spelling includes a system-prompt sentence stating it to the model (F5: the sentence promises the permitted local runtime and the remote tools, not "nothing can act on this machine").
- *Audit on the donor side:* the trusted bridge identity (CIP-0009 D1) writes one record per tool call it forwards: tool name, argument hash and size, timestamps, result size and exit, never arguments or environment; the records are owned by the bridge identity and readable by the donor; the harness cannot alter them.
- *Stop and leave:* `curator remote-worker stop` ends the harness processes and persists the stopped mark **before** anything else; `curator remote-worker leave` retires the workplace and keeps the identity; `curator remote-worker purge` destroys keys, configuration and home (CIP-0009 D7, F17). All are local commands of the donor under the bridge identity or the donor's own account; nothing on our side can prevent them.
- *Locked posture:* the donor's system configuration (manager §12) locks `tool_posture.remote-worker` with `permissions.remote-worker` as a pair (R1); a flag that conflicts with a locked member is a `usage` error (0018 item 2); `--tool-posture lockdown` on the command line may only tighten (`open → lockdown`), never loosen.

**R7. Conformance.** One vector per row of R3, per allowed tail option and per refusal class of R4, plus the production-entry negatives of the test plan, on the hosted lab runners (tb-R194: suites that spawn harness binaries do not run on the mini). **Acceptance evidence (F25):** the model-visible tool set is measured against the complete permitted set (`tools/list` and the harness's own tool inventory), alongside enforcement negatives; unknown audit coverage, an unknown tuple, a failed read of the protected settings file or missing sandbox support each refuse; mutation checks narrow the gate so that a broader unauthorized class demonstrably fails; `rwh` evidence is reused only for the releases and modes it states.

**R8. What this CIP does not claim.** On someone else's machine, no argument a launcher writes is a security boundary against that machine's owner, and a harness binary that could update itself would change its flags. The lockdown is the *declared and checked* posture; the enforced boundary is the OS confinement of CIP-0009 (separate identities, kernel sandbox, per-UID egress) plus the fact that the only capability with effect is the remote-tools relay, whose calls execute in our workplace under its policy. The remote harness stays untrusted in every case (architecture §7.9).

## Security considerations

- **Threat model.** The remote harness is compromised or prompt-injected. Goals: it must not read, write or execute on the donor's machine beyond its own managed home and scratch dir; it must not reach the network beyond the provider API; it must not reach the bridge's keys, audit or lifecycle state (separate identity, CIP-0009 D1); and whatever it does must be visible to the donor. **Credential posture (F22):** the provider credential is delivered into the harness process environment per launch (CIP-0010); a compromised harness can read it and pass it to a child inside its sandbox; eliminating the store copy limits the blast radius to one token, it does not make the token non-extractable. That is the owner-approved initial trusted-process posture (owner decision 2026-10-07: no provider interception in the first implementation); a stronger non-extraction mechanism needs a separately approved design.
- **Layers, in order of strength:** (1) separate OS identities, kernel sandbox and per-UID egress on the donor (CIP-0009); (2) no local tool offered to the model (R3); (3) the launcher grammar and the intake check of the expanded launch against the generated policy (R4, R5); (4) the executor's tripwire and audit of every tool name the model requests, as detection after dispatch (kept from `rwh`); (5) the workplace's own policy on our host (CIP-0009 D5, the `swarma-workplace-exec/1` contract). Layers 2–4 are posture and evidence; 1 and 5 are the boundaries.
- **Policy freshness (F9).** The plan binds the policy generation; the executor rechecks the current generation at exec and resume; a sandbox-profile revision in the plan proves which profile was requested, not that a process runs under it, so the executor's acceptance record carries the boot qualification separately.
- **Hostile repository.** Nothing in this CIP reads repository bytes to decide the posture; CIP-0002 strict project context keeps project files out of the managed launch, and the cwd is an empty scratch directory.
- **Secrets.** No secret enters argv, the plan or a fragment; the bridge's keys belong to the bridge identity (CIP-0009), not to the harness.

## Compatibility and migration

- Absent knob = `open`: every existing install and plan keeps its meaning. `permissions: remote-auto` is only valid with `lockdown`, so no existing configuration becomes invalid.
- **Composition ownership (F8).** There is no `--mode remote-worker` and no second flag compiler. Agents-management composes the lockdown launch through the one construction site (Decision 0019); the remote-worker supervisor of CIP-0009 **consumes** the composed plan as a session-host variant and never composes (Decision 0021); the interaction mode (interactive or headless) and the transport are independent axes of the launch contract, and posture is a target/posture field beside them. The amendments to 0019 and 0021 that name the supervisor as a fragment consumer, and the headless boundary question that LCH §9 raises, are adopted **before** implementation; LCH §9 is a proposal, not evidence that the decision has already changed.
- `rwh` migrates by replacing its hand-written flag recipes with the composed plan and keeping its tripwire, audit and `worker` guards as parts of the supervisor and the executor.

## Test plan

- Production-entry positive: `curator run <profile>` under a locked `lockdown` knob composes the plan of R3 for each tuple (golden argv, configuration, environment, plugin set) and the plan passes intake; the receipt prints posture, permissions, tuple and policy generation.
- Negatives: each allowed tail option passes and each refused class refuses with its code; `remote-auto` with `open` and `yolo` with `lockdown` refuse `usage`; a locked knob with a conflicting flag refuses `usage`; an unknown tuple refuses `tool_posture_unsupported`; a plan edited to add a built-in enabler, drop a required member, duplicate a flag or supply the same setting from a second source refuses `launch_plan_invalid`; a plan with a stale generation refuses `policy_generation_stale` at exec and at resume; an intake without the required extension refuses `launch_plan_unsupported_extension`; a vendor managed policy that enables a bypass refuses `tool_posture_conflict`; an unreadable protected settings file refuses.
- Behavioural (lab runners only): a fake model requesting `Bash`, `Edit`, `Write`, `WebFetch` gets an error tool result from Claude (`rwh` `TestTripwireOnExecutedBuiltin`), the same for Codex app-server (`unsupported call`) and Muse (refused at call time); a positive control with the posture off shows the marker files appear, so the test is not vacuous; the visible tool set equals the permitted set; a remote-tools call succeeds while a native approval is denied; no traffic leaves the harness UID except to the provider API; no update check or executable write occurs.
- Mutants: remove `--restricted`; keep `--tools ""` but add `--allowedTools Bash`; set `sandbox_mode = workspace-write`; drop `--disable-shell`; drop the intake expanded-launch check; drop the generation recheck at resume; widen the tail allowlist by one option. Each must be killed by a named vector.
- Platform matrix: macOS first for the donor side, Linux on lab runners; Windows later (owners' call C18).
