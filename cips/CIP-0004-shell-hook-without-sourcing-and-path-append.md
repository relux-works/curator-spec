Launcher and launch-fragment contracts require boundary clarification, not a PATH-policy change here.

## Summary

Adopt an interactive hook that discovers the project root and assigns its environment directly, without reading or sourcing project or global env files. Append the project `.agents/bin` at the end of PATH, after inherited entries and any optional global bin. Remove the warning-and-source exception immediately in the adopting revision, replacing the K3 staged A→B plan with a single `no-source-v1` contract. Preserve optional activation and opt-outs, retire approvals as an activation dependency, and make all human-facing paths and remedy commands safe to display. This draft asks for a design decision; it authorizes neither implementation nor scheduling.

## Motivation and user stories

1. Entering a checkout, including a nested directory or a symlinked checkout, must not execute its `.agents/env.sh` or `.agents/env.ps1`, even if an old approval record exists.
2. A checkout containing `git`, `ssh`, `curl` or `python3` in `.agents/bin` must not displace an executable already reachable through the inherited PATH.
3. Leaving or switching projects must restore PATH predictably, clear the old project root, and avoid duplicate hook registrations or bin entries.
4. A path containing shell syntax or terminal controls must not turn a notice into a second command or a forged terminal line.
5. An existing user must retain `--no-global` and `CURATOR_AUTO_ENV=0` when updating a cached hook, and must be told accurately whether the cache still contains the legacy hook.

Research bounds: one design decision, one CIP plus evidence below 100 KB combined, no archives or serial research prerequisite; an initial 60-minute worker budget. The frozen baseline is curator `ca1b776fb580ec0cee0173bf150daf063023aeaa` and curator-spec rc.14 `43bf0a2506d5c354a73bbc3ea4623d4653db10c7`. No new grammar is accepted by this research. The consuming production slice is L2 below: CLI-generated bash/zsh activation without sourcing, with append and restore tested together. Exit criterion is a decision-ready option comparison and proposed contract, not implementation conformance.

## Design

### Options considered

All three options must append PATH, remove every warning-and-source fallback, close the global sourcing exception, and repair display/command escaping. None can claim the stronger “repository code never runs” invariant merely by changing a profile name.

| Option | Mechanism | Benefits | Security, compatibility and cost |
|---|---|---|---|
| **A. B-enforcing by default + existing digest approvals** | Keep `approve`, `approvals`, `revoke`; trust canonical realpath plus digest. Unapproved, changed, unreadable or indeterminate candidates never execute. | Smallest conceptual migration; deliberately approved custom scripts continue to work. Existing unchanged records can remain meaningful after state validation. | Approving hostile code still authorizes its execution. Current hash-then-source has a TOCTOU window. All POSIX/Git Bash/PowerShell consumers need hardened state reads, global gating, safe notices and execution of the exact verified snapshot. Appended templates change digests; old approved prepending/custom scripts defeat the PATH guarantee unless invalidated or constrained. Least suitable for an unconditional no-repository-code invariant. |
| **B. Explicit verify-and-trust-on-first-use of canonical bytes** | An explicit verification command generates the manager's exact template for the shell and resolved root, compares bytes exactly, then records digest + realpath. The root is the only project-controlled template parameter; template version and shell are manager-selected. First use is verification, never blind approval. | Rejects arbitrary repository scripts even when their header claims to be generated. Can support a transition from canonical existing helpers. | Still needs an approval store, ownership/ACL rules and race-safe execution. A file can change after the command returns or between hook verification and sourcing. Execute an immutable private copy of the verified bytes, or manager-generated bytes, never reopen the repository path for execution. The latter converges toward C while retaining unnecessary state. Exact old prepending templates cannot remain automatically admissible. Three shell families require separate byte-exact templates, quoting and migration. |
| **C. Compute root and bin; source no env file — recommended** | Trusted generated hook performs metadata-only discovery, constructs literal root/bin values, assigns PATH and root variables, and maintains activation state itself. Global activation uses the same mechanism. | Removes repository shell parsing, approval-store dependencies and the env-file verification/use race. Hostile, changed, unreadable, symlinked or approved env files are irrelevant. Simplest default and warm path. | Custom env-file side effects cease to activate automatically. Must specify discovery, restoration, global order and cache migration. Appending still makes previously absent command names available; it is not a command sandbox. bash/zsh and PowerShell still require real-shell validation. |

For A and B, “digest + realpath” is necessary but insufficient: a retained store must reject symlinks, foreign owners, group/other writes, malformed/control-bearing records and uncertain reads; use a 0600 store in a 0700 directory. Apply the reviewer's conservative macOS rule: any ACL marker `+` rejects the store, as does an inability to inspect it; specify an equivalent native Windows ACL policy before qualification. Cached checks must not survive inode/size/mtime/ctime changes, including same-size same-second writes; only cache strictly older timestamps at the finest available resolution. Even that metadata policy does not make reopening the path race-free. A retained installer must warn on approval-store trouble rather than turn an already committed installation into a reported failure; curator's post-commit recording already follows that rule (C5). These are obligations if A/B is chosen, not claims about present coverage.

Snapshot execution also changes compatibility: today's POSIX canonical helper discovers its root from its own source location (C1), so simply copying it to a private approval directory changes the root it computes. B needs a new canonical template with the verified project root encoded as a literal; A cannot transparently relocate every arbitrary approved script that depends on its source filename. This is another cost of retaining sourcing, not a solved property of a digest store.

### Recommendation

Select **C**, with one supported behavior, `no-source-v1`, and no configurable unsafe mode. In particular `_CURATOR_TRUST_PROFILE`, an old record, a file header or a “permissive” security profile must not re-enable sourcing.

**Discovery and roots.** The nearest ancestor containing a `.agents` directory is the project root; a symlink to a directory counts. The hook examines metadata only and never opens an env file, Skillfile, approval store or launch fragment. Start from the physical current directory; validate POSIX `PWD` is absolute and non-empty first, then obtain the physical location using shell builtins. Return one absolute physical root independent of checkout aliases. Preserve literal bytes, including trailing newlines when capturing shell output. A missing marker continues the bounded parent walk; an inaccessible/indeterminate directory stops activation, not a fallback to a different project. `.agents/bin` may be absent at discovery: its literal path can be appended and becomes usable after installation. An env file's absence or unreadability cannot prevent activation.

**PATH ownership and order.** From a clean inherited PATH, render `inherited → global/bin → project/.agents/bin`, omitting disabled scopes and adding no duplicate entry. The project addition is the last entry. Joining an empty or unset PATH introduces no empty component; preserve the original set/unset state for restoration where the shell supports it. Record the exact pre-activation PATH and which entries were added. Repeated activation is a no-op; switching first removes the previous activation and then appends the new project; leaving or opting out clears `CSK_PROJECT_ROOT` and project state, retaining only a still-enabled global scope. Never remove a bin entry already present before this hook acquired it. Keep rc.14's snapshot-restoration semantics for independent PATH edits made while a scope is active; preserving arbitrary concurrent edits is not claimed by this revision. Test that boundary explicitly instead of inferring ownership from substring replacement.

This order changes the current project-over-global precedence: a global command wins a name collision with a project command, while both lose to inherited commands. A user who needs a particular project command uses its portable explicit path. A bin already put at the front by the user's profile or an old manually sourced helper is inherited state; the new hook cannot promise to repair that history. Migration must explain this limitation.

**Global activation and controls.** Compute `<manager-home>/global` and its bin without sourcing `global/env.sh` or `global/env.ps1`. Bind an absolute manager-home from the CLI-selected configuration location when generating/loading the hook; never reinterpret a relative config location after each `cd`, and never parse config contents at a prompt. Preserve `--no-global` and the runtime `CURATOR_AUTO_ENV=0` project-scan opt-out. No new public configuration knob, approval command or trust store is required for activation. The manager-owned cached hook itself remains executable code explicitly loaded by the user's profile, under the existing manager-install trust boundary.

**Unrepresentable paths.** POSIX PATH cannot encode a directory containing `:` as one entry; Windows PATH cannot encode one containing `;` as one entry. Refuse automatic activation of that scope, leave the caller's PATH unchanged, and emit a fixed one-line diagnostic with no interpolated path from the prompt hook. Do not split such a name into multiple search directories. NUL cannot be represented as an environment value; CLI/data readers reject it. Spaces, globs, quotes and other representable path bytes are literal data.

**Shell integration.** Keep bash string/array `PROMPT_COMMAND`, zsh `precmd`/`chpwd`, and PowerShell prompt wrapping. Preserve registration idempotence, existing prompt output and an in-progress guard. Use builtins and quoted literal operands; external utilities, if unavoidable, use a trusted system search (`command -p` on POSIX), never project PATH. zsh hook functions run on directory changes and alias expansion happens when functions are read, so qualifying runtime calls alone is insufficient: establish alias-safe parsing as well ([zsh Functions](https://zsh.sourceforge.io/Doc/Release/Functions.html)). PowerShell uses literal filesystem operands, native path separators, and module-qualified commands or .NET APIs; it must not rely on ambient aliases/functions. No manager subprocess is required on the warm prompt path.

## Security considerations

The attacker controls checkout names, env files, `.agents` contents and symlinks, and may forge repository-local approval records. Trusted inputs are the installed manager/generator, its cached hook and the user's preexisting shell environment. The change makes directory/prompt activation incapable of executing repository or global env-file bytes. No approval or verification/use interval exists for those bytes. It does not make the filesystem immutable or authenticate executable shims: symlinks/bin contents can still change before an explicitly requested command runs.

Appending protects the precedence of inherited executables, not aliases/functions or command names missing from the inherited PATH. Existing manager provider trust-root checks, reserved command names and explicit launcher boundaries remain necessary. Environments §11's provider policy must not be weakened on the assumption that append solves all executable discovery (S4). PowerShell resolves aliases/functions/cmdlets as well as external commands; native negative tests must account for that documented order ([command precedence](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_command_precedence?view=powershell-7.5)).

**Display is separate from execution.** Prompt activation is silent on success and needs no approval notice. Any remaining CLI status, install notice, error or deprecated approval output must use an ASCII-safe path display: escape C0 controls, DEL, raw C1 bytes, Unicode C1/bidi controls, Unicode line separators and invalid encodings; escaping all non-ASCII bytes/code points is an acceptable locale-independent policy. Escape backslashes too, and bound/truncate display only with an explicit truncation mark. A diagnostic must remain one physical line in both C and UTF-8 locales. Underlying error strings are untrusted display inputs too.

A displayed escaped path is not automatically an executable shell argument. For printable ASCII operands, printed copy-paste commands use single quotes: POSIX replaces an embedded apostrophe with `'"'"'`; PowerShell doubles it. Use `--` where the target command accepts it. Never use bare or double-quoted untrusted operands. For operands requiring control/non-ASCII escaping, omit the path-bearing executable hint and give static instructions, rather than printing a lossy command or raw controls; generated machine-consumed hook code must still encode its constants losslessly. This also avoids PowerShell's additional smart-quote parsing rules ([quoting rules](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules?view=powershell-7.5)). Test copying every emitted executable hint in a fresh real shell.

No credential, token, Keychain entry or operator configuration content is required for this research or for the hook. All probes used newly created scratch homes and synthetic payloads. Findings belong in this CIP, its evidence and task notes; `LOGBOOK.md` is explicitly out of scope under the binding task instruction.

## Compatibility and migration

1. **Existing env helpers:** keep them as deprecated, explicit-use compatibility artifacts for one release; new manager-generated bytes append and handle empty PATH in both scopes/shells. The automatic hook ignores all of them. Do not inspect custom env contents merely to activate a directory, and do not describe manual sourcing of an arbitrary repository file as safe. Existing old bytes are not silently rewritten by read-only status; regeneration occurs through existing write/install operations. Custom variable exports move to an explicitly controlled user setup outside automatic repository activation.
2. **Existing approvals:** ignore them during activation, stop manager recording of new shell approvals, and leave old state on disk for an explicit cleanup decision. `approve` must not report that it enabled activation: retire it with an explanatory non-zero result and no new record. `approvals`/`revoke` may remain deprecated inspection/cleanup commands for one release, with escaped human output. No config, Skillfile, marker or launch-fragment schema bump is needed merely to stop sourcing. Approval-state schema changes are unnecessary for C.
3. **Cached hooks:** a binary update alone cannot repair an already cached script. Add manager-owned cache metadata, proposed closed shape `{schema_version: 1, shell, hook_revision: "no-source-v1", include_global: bool}`; this is generation metadata, not an approval store. Refresh only existing managed caches during the applicable install/update path, and preserve their `include_global` selection. For `shell-init --install`, omission of `--no-global` preserves a recognized existing cache's choice; first installation defaults to global enabled. An explicitly supplied `--no-global` disables it, and `--no-global=false` re-enables it, using the existing boolean flag rather than a new mode. Direct non-cached generation retains its explicit flag/default semantics. `CURATOR_AUTO_ENV` remains a runtime choice. For old caches without metadata, infer options only from exact known legacy generated bytes; never source the cache to discover options. Unknown/custom or unreadable caches are reported as legacy/unknown and require explicit regeneration with an explicit global choice, without failing an otherwise committed package install or claiming the cache is current.
4. **Reloading:** new shells using refreshed caches get the new contract. Existing shells keep loaded old functions until reload/restart; old global prefixes cannot always be distinguished from user-owned entries. Recommend a fresh shell with a clean profile after refresh; do not promise complete live-state cleanup. Direct profile lines sourcing `.agents/env.*` also require user removal. Installation must not edit a user profile automatically.
5. **Status and versioning:** report `hook-trust=no-source-v1` with shipped provenance and separately report managed-cache revision/currentness. A cache is current only when its actual bytes equal the generator's canonical output for its retained options and manager-home binding; metadata or a revision comment alone is insufficient. A partial cache/metadata publication is non-current. A manager executable's shipped revision is not evidence of a live shell's loaded code; that state is unknown unless explicitly observed. Stop using env-file digest drift to fail `--check` for the new hook; obsolete/unknown managed caches remain actionable. Version the new conformance contract and retain rc.14 vectors as historical, not simultaneous requirements.
6. **Windows:** include Git Bash path spelling and native PowerShell. Keep the currently supported shell families; native Windows PowerShell 5.1 behavior and PowerShell 7 must be tested or explicitly revised by the operator, not silently replaced by a macOS `pwsh` run. Use the platform's PATH separator; distinguish empty/unset according to runtime capabilities ([PowerShell environment variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables?view=powershell-7.5)).

## Specification changes

The following is a normative sketch to publish in curator-spec only after review and operator acceptance:

> **Manager §8, no-source-v1.** Shell activation is optional. A hook MUST NOT source, dot-source, evaluate, import or otherwise execute any project or global env-file content. No approval record or rollout mode may relax this rule. Discovery MUST use directory metadata and MUST NOT depend on env-file bytes, readability or approval. The nearest `.agents` directory identifies the physical project root; invalid or indeterminate discovery disables activation for that scope. The hook MUST append its bin entries after inherited PATH entries, with the project bin last, MUST NOT introduce empty entries, and MUST clear project-root state when leaving. Reloading MUST be idempotent. Global activation follows the same no-source rule, is enabled by default, and respects an explicitly retained opt-out.

> **Manager §§3 and environment exposure.** Newly generated optional env helpers append their scope bin and correctly join empty PATH; they are deprecated explicit-use compatibility artifacts. Automatic activation does not consume them. Interactive PATH ordering is inherited, optional global, optional project. The command-launcher child-environment rules remain separately scoped: this CIP does not change the self-contained launcher prepend at §3 lines 665–669, enforced-worker PATH construction, or the reserved launch-fragment `path_prepend` field.

> **Manager §§8.1–8.7 and §10.** Replace the approval gate, warning diagnostics and A/B rollout contract with no-source behavior, safe output, cache migration/currentness and real-shell execution vectors. Retain legacy approval CLI only as explicitly deprecated inspection/cleanup. The `hook-trust` posture value is `no-source-v1`, with `shipped` provenance; it must not attest live-shell state. Introduce a closed diagnostic for unrepresentable/indeterminate activation and cache migration states as needed, without raw path output. Update the compiled-repository environment-exposure prepend sentence (S6) to distinguish interactive append from explicit launcher construction.

> **Environments §§11–12.** Describe historical S6/K3 env-file execution as removed by Manager §8's new hook while retaining the provider trust-root requirement for all untrusted PATH entries. Cross-reference `no-source-v1` in the shared posture inventory and distinguish cache status from live-shell status. Do not revise Environments §9.2's independent update-confirmation A→B plan, §10.2's reserved `path_prepend`, or §11's provider rollout through this decision.

**Proposed decision record — replace the K3 warn-first plan.** Status: Pending operator acceptance. Context: rc.14 Manager §8.5 requires warning-and-source before enforcement; measured directory entry executes hostile bytes and prepend displaces inherited commands. Decision: adopt C, with no-source activation and append together in the adopting release; supersede §8.5's staged A→B rule only for shell activation/K3. Consequences: custom automatic env scripts and approval authorization end; helpers/approval cleanup get a bounded deprecation window; caches and open shells need explicit migration; inherited-before-global-before-project becomes normative. Rejected alternatives: A keeps arbitrary approved code and verification/use risk; B restricts code but retains store/snapshot complexity. Acceptance must name the target release and approve the global collision behavior. The orchestrator assigns the decision filename/number when publishing this reviewed CIP under `cips/`; this research edits neither spec nor decision files.

## Open questions for the operator
