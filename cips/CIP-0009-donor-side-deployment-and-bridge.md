## Revision 2: what the architecture review changed

- **F10:** the harness and the bridge no longer share one OS user. The donor side has an **untrusted harness identity** and a **trusted bridge identity**; keys, audit, lifecycle state, the SSH client and the signer live in the bridge identity; the harness reaches it only through a minimal stdio relay and an authenticated local socket with peer credentials (D1).
- **F11:** the OS setup is an executable, qualified capability on one platform first (macOS), with an explicit service domain, account lifecycle, key-unlock strategy, protected executable roots, writable state roots, a mandatory read boundary with explicit runtime exceptions, transactional provisioning and rollback; unsupported hosts refuse (D2).
- **F12:** the MCP declaration pin covers declaration content only; the executed binaries are pinned and verified separately by absolute path from a protected root; the allowlist entry is a canonical source identity; installation is an explicit operator-owned provisioning contract (D3).
- **F13:** the bootstrap has a versioned, domain-separated transcript, a server challenge, atomic invitation consumption with replay tombstones, cryptographically random codes with attempt limits, separate keys per role, standard authenticated encryption, a root-validated operator chain, and an explicit DNS validation model; the first release bootstraps trust from the out-of-band pin (the invitation plus the human fingerprint check) and treats DNSSEC/DANE as a cross-check where a trusted validator exists; nothing downgrades on failure (D4, D6).
- **F14:** SSH authorization lives outside the workplace user's write authority, the forced command is an absolute protected path, unneeded SSH features are disabled in the qualified server policy, host pins are rechecked on every reconnect with no trust-on-first-use, and the privileged helper has a closed operation schema with allocated identifiers and safe paths (D2, D4, D5).
- **F15:** `swarma-rb/1` defines bounded frames, canonical encoding, version negotiation, connection-scoped ids, idempotency keys with a result cache for uncertain results after reconnect, server-authoritative caps, method authorization, ownership rules for `cancel` and `stdin`, backpressure, and job lifetime ownership with leases and proven descendant cleanup (D5).
- **F16:** the first backend is named (the OS-user workplace of VISION v1.3) and its contract `swarma-workplace-exec/1` is specified with the guarantees it must give; RWP's container conformance is not borrowed; the effective tool set is the intersection with the workplace policy; mailbox methods are control plane, not tools by default (D3, D5).
- **F17:** `stop`, `leave`, `purge` on the donor and `suspend`, `retire`, `revoke` on our side are separate transitions with defined ordering; the identity is preserved unless revoked; the donor is told the revocation outcome (D7).
- **F18:** the project bridge never signs as the donor-held worker key: the **donor-side bridge signs the final envelope bytes** with the worker's signing key; our side verifies, admits and carries the bytes unchanged under a distinct, audited carrier authority (D5).
- **F19:** delivery has host-side admission on the donor, a qualified session-input adapter for control turns, advisory and bounded notifications, durable cursors on both sides, acknowledgement after persistence, reconnect catch-up, deduplication, and an application receipt distinct from the transport receipt; disconnected behaviour is defined (D5).
- **F25:** the rollout starts with the one-host MVP slice (separate keeper, broker and worker identities on our host) before any donor; the cuts for the first delivery are listed (§Implementation plan).

## Summary

This CIP specifies the **donor side** of a remote worker and the **bridge** between the donor's machine and the project's host: what Curator installs on the donor machine at first deployment (two OS identities, a kernel sandbox and a per-UID egress policy, a locked machine configuration, a trusted bridge service and a minimal remote-tools relay), how the initial exchange works (invitation, three role-separated keys, a signed enrolment transcript over a server challenge, join point, out-of-band fingerprint check, root-signed admission, an authenticated-encrypted credential package), how the harness talks to our host (one SSH connection from the donor's bridge identity towards our host, carrying the framed `swarma-rb/1` protocol and the mailbox), how MITM and replay are defended (pin bootstrap plus DNS cross-check, pinned keys both ways, signed transcripts and envelopes over exact bytes), and how a worker is stopped, retired, revoked or purged on both sides. It decides that the remote tools are an **MCP relay** while the initial exchange is a **Curator CLI step**, never a tool the model can call. Diagrams: `diagrams/donor-first-deployment.puml`, `diagrams/join-handshake.puml`, `diagrams/remote-worker-turn.puml`, `diagrams/remote-worker-retire.puml`, `diagrams/donor-side.dsl` (C4 containers).

## Motivation and user stories

- **Owner (2026-10-08):** "Curator on the donor machine manages the MCP setup, including a local MCP server for the remote tools, at first deployment of the environment"; "what the donor sees, how they stop it, what is logged on their side"; "the full set: handshake, join point, DNS fingerprints, MITM, Remote Bash, mailbox, retire, with diagrams".
- **A person who downloaded our toolchain** and wants to run their agent on our task: one invitation, one command, a visible result ("registered, waiting for tasks"), and a way out that does not depend on us.
- **Our orchestrator** wants the remote worker to be an ordinary worker: pin-checked launch, mailbox tasks, results as outcome proposals, no commands ever sent towards the donor's machine (architecture §7.9: connection towards the host only, C19).
- **Both owners** want one strong boundary and few moving parts (remote-workplace design rule). The review showed that "few moving parts" must not mean "one OS user": the boundary the owners want needs two identities on the donor.

## Current state

- `rwh` (relux-works/remote-worker-harness) runs Claude, Codex and Muse on the dedicated Mac mini with the built-ins locked (CIP-0008 §Current state) and the tools served from the project machine over `ssh -R` (a reverse-forwarded Unix socket) or through a relay; its `rwh worker` mode turns addressed a2a messages into turns under allow-from, budget and rate guards; for Muse it already measured a **stdio relay over a Unix socket** with the Seatbelt profile. The tunnel is opened **by the project side into the remote machine** and the remote machine is *ours*; nothing exists for a foreign donor, and the host side keeps no per-worker OS user (that is the remote workplace of architecture §7.9, designed in VISION v1.3 and not yet implemented). `rwh`'s Codex path is a single auth owner with an explicit lock and external access tokens for tenants (CIP-0010 C2).
- relux-works/remote-workplace v2.1 (RWP) gives a **container** host side of tool execution: a fresh hardened container per call inside a dedicated VM, a per-worker policy (tools, write scope, network mode, limits), change extraction as a reviewed patch, an egress service, audit and cleanup. Its guarantees belong to that path (RWP §1, §9) and are not inherited by an OS-user executor whose tool names look alike. VISION v1.3 §0 and the owners' call (C9) choose an **OS-user workplace** on our host for the first implementation, while the architecture diagram `remote-worker-start` still depicts the container path: a source reconciliation the owners should settle when adopting this CIP.
- Curator today: no `remote-worker` commands; MCP declaration packages are `git`-sourced `agent-mcp.json` with `stdio` (bare command on `PATH`) or `http` (`https` only) transports, bounded by `mcp_package_allowlist` entries that are **canonical source identities** (§2.2); the manager never installs or launches a server (§2.2); first-party modules have roots (Decision 0009); CIP-0007 proposes operator-trusted provisioning of binaries; the umbrella provider at revision A warns rather than refuses on a provider outside trusted roots.
- Keys: the key keeper of architecture §7.2 is design; `curator-trust` is a v0.4 draft; today's a2a uses per-agent Matrix accounts with tokens in `~/.config/a2a-swarm/` (0600).

## Design

### Options considered

**A. Where the remote tools live**
1. *MCP server on our host, reached by the harness over `http`* (environments §2.2 `http`). The harness would need a network path and an authentication secret it holds itself. Rejected.
2. *One local MCP server in the harness's OS user, holding the SSH client and the keys* (revision 1). The review showed it defeats the separation the design claims: a shared UID cannot be told apart by a per-UID firewall, the shared home exposes audit, state and (on the file fallback) the private key, and a keyring item is not a non-exportable signing service. Rejected.
3. *A minimal stdio **relay** in the harness identity plus a trusted **bridge service** in a second identity, joined by an authenticated local socket with peer credentials.* The harness sees a local process with no keys and no network; the bridge holds everything that must not be reached. `rwh` measured the relay shape for Muse. **Recommended.**
4. *Curator skill with scripts.* Scripts need a local shell, which the lockdown removes. Rejected for tools; kept for prompts.

**B. How the donor receives tasks and messages**
1. *A carrier client (Matrix) on the donor machine.* Mirrors our bridge, but puts carrier credentials on a foreign machine and adds a second network path. Later option.
2. *Mailbox over the tool channel.* The same SSH connection carries the mailbox control frames; the worker's **carrier** account lives in **our** bridge (C2 of the owners' call: the agent never reads the carrier), while the worker's **signing** key stays on the donor and signs every outbound envelope (F18). The donor holds no carrier credential at all. **Recommended for the first release.**

**C. The initial exchange**
1. *An MCP tool `enrol`.* The model would see the key material or at least drive the exchange. Rejected.
2. *A Curator CLI step run by a human on the donor machine* (`curator remote-worker init <invitation>`), with the keys generated by the bridge identity and never readable by the harness. **Recommended.**

**D. Trust bootstrap for the first contact**
1. *DNSSEC-validated TXT/SSHFP/TLSA as a hard requirement.* Sound only with a trusted validating resolver on the donor (an AD bit from an arbitrary upstream resolver proves nothing); adds DANE implementation scope to the first release. Kept as a cross-check.
2. *Out-of-band pin bootstrap:* the invitation carries the root fingerprint and the SSH host key fingerprint, the human compares the worker fingerprint over a second channel, and everything after is pinned. **Recommended for the first release**, with DNSSEC/DANE cross-checks when a trusted validator exists and as the long-term rotation channel.

### Recommendation

**D1. Components on the donor machine** (C4: `diagrams/donor-side.dsl`).

| Component | Runs as | Job |
|---|---|---|
| `curator` (donor install) | the donor (the machine's owner) for `init`, `leave`, `purge`; the bridge identity for `run`, `status`, `stop` | first deployment, status, stop, leave, purge; requests the composed lockdown plan from the construction site (CIP-0008 §Compatibility) |
| privileged helper (`swarma-helper`) | root for one command (sudoers rule limited to this absolute path) | a **closed operation schema**: `create-worker`, `remove-worker`, `set-egress`, `apply-sandbox`, `rollback`; allocates the two accounts and their identifiers from its own range (the caller passes only the project label, validated as `[a-z0-9-]{1,32}`); fixed templates for firewall and sandbox profiles; refuses any other input; writes a provisioning journal and rolls back a failed step; never removes a pre-existing account |
| harness identity `swarma-rw-<project>` | — | the **untrusted** side: home 0700, no password, no interactive login, process and disk quotas; owns only the managed home and the scratch dir |
| bridge identity `swarma-rb-<project>` | — | the **trusted** side: owns the keys, the pinned configuration, the audit log, the lifecycle state, the SSH client and the signer; its home is unreadable by the harness identity |
| bridge service (`swarma-bridge`) | the bridge identity, as a system service (macOS: `launchd` daemon with `UserName`; it survives logout and needs no login session) | holds the one SSH connection to our host; serves the relay over an authenticated Unix socket (peer credentials checked: only the harness identity of this project may connect); signs outbound envelopes; admits inbound mailbox items; counts budgets; writes audit; executes `stop` |
| remote-tools relay (`swarma-remote-tools`) | the harness identity | a `stdio` MCP server with **no keys and no network**: it forwards `tools/call` to the bridge socket and returns results; its tool list is what the bridge reports as the effective set (D3); refuses everything else with an error result and an audit line (sent to the bridge) |
| remote-worker supervisor (`curator remote-worker run`) | the bridge identity (part of the bridge service) | consumes the composed lockdown plan (never composes), launches the harness **as the harness identity** under the sandbox profile, turns admitted mailbox items into turns through the session-input adapter, posts results, enforces budgets and lifetimes (the `rwh worker` guards: allow-from, daily tokens, rate, ping-pong, turn timeout, lifetime) with the trusted-side counters as the authority |
| egress policy | kernel | harness identity: loopback to the local provider proxy only; bridge identity: our SSH host and our join point only; nothing else, nothing inbound |
| provider proxy | the bridge identity or a system service | the harness's only path to the provider API: a host allowlist per qualified tuple; no other destination |
| locked machine configuration | files owned by the bridge identity, read by Curator | `tool_posture.remote-worker: lockdown`, `permissions.remote-worker: remote-auto` (the lockable pair of CIP-0008 R1), `policy_generation`, `mcp_package_allowlist: [<canonical source identity of swarma-remote-tools>]`, `passable_env_names: []`, the qualified tuple, the project binding (host, SSH host key fingerprint, root fingerprint), the sandbox profile revision |

Everything the first draft put "in the same user, protected by the keyring's access control" is now in the bridge identity. The harness identity cannot read the bridge's home, cannot connect to anything but the relay socket and the proxy, and cannot alter any control state; this is true by UID and sandbox, not by promise.

**D2. OS sandbox and provisioning (F11, F14).** One platform is qualified first: **macOS** (the platform `rwh` measured). Linux follows with its own qualification; Windows is out of scope (owners' call C18). Unsupported hosts refuse at `init`.
- *Accounts:* two hidden accounts without login shell or password, created by the helper with allocated UIDs; the bridge account's home holds the keys (0600 files owned by the bridge identity in the first release; keyring-backed non-exportable keys are a later hardening, since a headless daemon cannot rely on a login keychain) and the state; the harness account's home holds the managed home and the scratch dir.
- *Service domain:* the bridge service is a `launchd` system daemon running as the bridge identity, so it starts at boot, survives logout and does not need a user session; the harness is launched by the bridge service as the harness identity.
- *Egress:* a `pf` anchor with per-UID rules (harness → loopback proxy port only; bridge → our SSH host and join point only; everything else blocked both ways). Because the identities are distinct, UID rules are meaningful.
- *Sandbox:* a Seatbelt profile applied to the harness process with an explicit allow-list: read and execute of the pinned executable root and its runtime libraries, read and write of the managed home and the scratch dir, connect to the relay socket and the proxy port; deny everything else (file reads, AppleEvents, pasteboard, LaunchServices `open`, other sockets). The **read boundary is mandatory**, not "where available"; it is what makes Muse's retained read tools harmless and what keeps the bridge's home unreadable even if the file permissions were wrong. The profile revision is part of the qualified tuple (CIP-0008 R3) and of the plan (R5).
- *Protected executable root:* `/opt/swarma/<release>/` owned by root, read-only, no writable predecessor directory; the bridge launches every binary (harness, relay, proxy, itself) by absolute path from it and verifies the digest against the pinned release manifest first (D3).
- *Transactional provisioning:* the helper journals each step (accounts, homes, egress anchor, sandbox profile, daemon unit) and `rollback` undoes a failed provisioning in reverse order; a half-provisioned machine never keeps a relaxed rule; `init` reports the exact step that failed.
- *Linux (second platform):* two system users with `nologin`; `nftables` with `meta skuid`; the bridge as a `systemd` system service; the harness started through `systemd-run --uid` with `NoNewPrivileges`, `PrivateTmp`, `RestrictAddressFamilies`, a cgroup for lifetime ownership, and **Landlock** as the read boundary (ProtectSystem is a write boundary, not a read-confidentiality one); the managed home mounted writable, the executable root read-only. Qualified separately before any Linux donor.
- *Negative tests per platform* at the real `init`, launch, tool and stop entries: reads outside the allow-list refused, egress outside the allowlist refused, the proxy refuses a non-provider host, the relay socket refuses a connection from another UID, the helper refuses a second account with the same label, a symlink in a path argument, an arbitrary user name in `remove-worker`, and an injected argument; provisioning interrupted halfway rolls back; a pre-existing account with a colliding name is never removed.

**D3. The relay as a declared package; the executable pinned separately (F12, F16).** `swarma-remote-tools` is a first-party module (Decision 0009) shipped with the toolchain, declared to profiles as an MCP declaration package (`agent-mcp.json`, `transport: stdio`, `command: /opt/swarma/<release>/bin/swarma-remote-tools` as an absolute path, no `env_names`), pinned in the profile lock like any package, and the only entry of the donor's locked `mcp_package_allowlist`, which names its **canonical source identity** (environments §2.2), not a package name. The pin covers the declaration; the **executable** is covered by the release manifest: the bridge verifies the digest of every binary it starts and refuses a changed, unreadable or shadowed file (`executable_unpinned`). Installing the binaries on the donor is part of the operator-owned provisioning contract of `init` (CIP-0007 shape); the manager boundary of §2.2 ("the manager never installs or launches a server") is amended deliberately for this provisioning step and for nothing else.

The relay's maximum tool set and where each executes:

| Tool | What it does | Executes where |
|---|---|---|
| `bash {cmd, cwd?, timeout_s?, max_output_bytes?}` | an `exec` request on the channel | our host, inside the workplace under its policy |
| `read_file`, `write_file`, `apply_patch` | file operations inside the workplace | our host |
| `mailbox_read {cursor?}` | fetch admitted messages with their verification records | the donor bridge's admitted mailbox view (D5) |
| `mailbox_post {binding, text}` | post an outbound message signed by the worker's key | signed on the donor, carried by our bridge (D5) |

The **effective** set offered to the model is the intersection of this list with the workplace policy of the worker (`tools` of the policy, fetched at connect and refreshed on `policy.changed`): a read-only worker gets `read_file` only, not `bash`, `write_file` or `apply_patch`. Mailbox operations are **control plane** between the bridge service and our bridge; `mailbox_read` and `mailbox_post` appear as tools only when the policy grants them, and the supervisor delivers task turns through the session-input adapter, not through a tool the model has to call (F19). No `enrol`, no `key`, no `config`. Any other `tools/call` is an error result and an audit line.

**D4. First deployment** (`diagrams/donor-first-deployment.puml`, `diagrams/join-handshake.puml`; F13).
1. We issue an **invitation** `swarma-invitation/1`: `{invitation_id (128-bit random), join_point_url, root_fingerprint, ssh_host_key_fingerprint, project, role, expires_at, code}`. The `code` is a cryptographically random one-use bearer bootstrap capability (at least 128 bits, base32), and the CIP says so: it is a secret for the duration of the enrolment, delivered to the human over a second channel (chat, voice), limited to a few attempts, and consumed atomically.
2. The donor (the machine's owner) runs `curator remote-worker init <invitation-file>`. Curator refuses unsupported hosts, calls the helper (D2: accounts, homes, egress, sandbox, daemon), and the bridge identity generates **three keys**: `K_sig` (Ed25519, signing), `K_enc` (X25519, package decryption), `K_ssh` (Ed25519 SSH key). It builds the enrolment certificate `{K_sig, K_enc, K_ssh, name, role, invitation_id, expires}` self-signed by `K_sig` and shows the fingerprint (SHA-256 over the certificate bytes) to the donor.
3. *Challenge:* `POST /join/challenge {invitation_id}` → the join point returns a server challenge bound to the invitation (random, five-minute lifetime, attempt counter). *DNS cross-check:* when the host has a trusted validating resolver (local validator or a validating stub over a protected channel), Curator fetches `TXT _swarma.<domain>`, `SSHFP` and `TLSA` and requires **secure** results that equal the invitation's fingerprints; a **bogus** result refuses; an **indeterminate** result (no trusted validator) proceeds on the pin bootstrap alone and records that fact in the enrolment; there is no downgrade from secure to anything.
4. *Transcript:* the client builds the canonical `swarma-join/1` transcript (deterministic CBOR, domain-separated): `{version, invitation_id, project, role, K_sig, K_enc, K_ssh, server_challenge, client_nonce, expires_at, algorithms}`, signs it with `K_sig`, and sends `POST /join/cert {transcript, signature, code}` over TLS pinned to the join point's certificate named in the invitation (and cross-checked by TLSA when available). The join point verifies the code in constant time, the signature, the challenge binding and the expiry, **consumes the invitation atomically** (a tombstone keyed by `invitation_id` prevents replay; a retry with the same `K_sig` returns the same pending enrolment, a retry with a different key refuses), rate-limits per address and per invitation, and stores the pending enrolment. The join point accepts only `challenge`, `cert` and `collect`; no commands.
5. *Human check and admission:* the operator (or an orchestrator with the `onboard` grant plus operator confirmation) **compares the fingerprint over the second channel**, pins `K_sig`, `K_enc` and `K_ssh` in the registry, has the root sign the admission record, issues the grants (post to the project room's worker thread, read own mailbox, no delegation, expiry), and builds the **credential package** `swarma-credential-package/1`: `{our root public key, operator certificate (root-signed, scope onboard, validity), host, SSH host key, workplace user name, binding digest, qualified tuple, policy generation, expires}`, encrypted to `K_enc` with standard authenticated encryption (X25519 key agreement, HKDF, ChaCha20-Poly1305) with the transcript digest as associated data, and signed by the operator certificate.
6. *Collect:* `POST /join/collect {invitation_id, signature over a second server challenge by K_sig}` → the package. The bridge identity decrypts, verifies the operator certificate against the pinned root (the root fingerprint the invitation named, cross-checked by DNS when secure), verifies the package signature, checks the associated data, writes the locked machine configuration and the project binding, installs the relay declaration into the `remote-worker` profile, and prints "registered; waiting for tasks".
7. Our dispatcher provisions the workplace (an OS user on our host; the worker's `K_ssh` in a **root-owned** `AuthorizedKeysFile` outside the workplace user's home with `restrict,command="/opt/swarma/bin/swarma-rb-exec"`; egress per UID), as in `remote-workplace-attach`.

**D5. The bridge** (`diagrams/remote-worker-turn.puml`).
- *Connection (F14):* the bridge service opens **one SSH connection from the donor machine to our host**, as the workplace user, with `K_ssh`; the host key is checked on **every** connection against the pinned key from the package (and SSHFP when secure); there is no trust-on-first-use. On our side a `Match User` block for workplace users sets `AuthorizedKeysFile /etc/ssh/swarma/%u` (root-owned, so a workplace user cannot add a key through a shell tool), `PermitUserRC no`, `PermitUserEnvironment no`, `AllowAgentForwarding no`, `AllowTcpForwarding no`, `X11Forwarding no`, `PermitTTY no`, and the forced command by absolute path; `restrict` in the key options adds the same. Our host never connects to the donor and never sends commands into the donor's machine; the bridge service reconnects with backoff after a drop.
- *Framing `swarma-rb/1` (F15):* one multiplexed channel over the SSH session. A frame is a 4-byte big-endian length (bounded **before** allocation; maximum 1 MiB) followed by deterministic CBOR with canonical field types, no duplicate keys and byte strings for binary data. The first frames are `hello` with version negotiation (`versions: [1]`; an unknown version refuses and closes). Every request carries a connection-scoped monotonic `id` and a client-chosen `op_key` (UUID) that makes side effects idempotent: the server keeps a result cache per binding keyed by `op_key` for ten minutes, so a reconnect after an `exec` or a `mailbox.post` whose reply was lost returns the cached result or `unknown_result` and never replays the effect. Requests: `exec {cmd, cwd, env: {names from the policy's env_allow only}, timeout_s, max_output_bytes, lease_s}`, `cancel {target_id}`, `stdin {target_id, bytes}`, `file.read`, `file.write`, `patch.apply`, `mailbox.read {from_cursor}`, `mailbox.post {envelope_bytes, signature}`, `mailbox.applied {message_id}`; replies `stdout|stderr {seq, bytes}`, `exit {code}`, `error {code}`, `result`, server-initiated `mailbox.notify {message_id, cursor}` (advisory) and `policy.changed`. **Server policy is authoritative:** a caller may lower `timeout_s`, `max_output_bytes` or `lease_s`, never raise them above the workplace policy; `cancel` and `stdin` apply only to a live job owned by the same binding; each method is authorized against the policy; a window of outstanding frames and `flow` credits give backpressure; `env` names outside `env_allow` refuse.
- *Job lifetime:* every `exec` runs in its own process group (Linux: also a transient cgroup) with a server-side lease; the lease expiring, a `cancel`, or the transport dropping after a grace period kills the group and verifies that no process of the workplace UID descends from the job; descendant cleanup on transport loss is a test vector, not an assumption.
- *Backend contract `swarma-workplace-exec/1` (F16):* the first backend is the **OS-user workplace** of VISION v1.3 (one OS user per worker on our host, egress per UID). The contract names what every backend must give: an execution API with the caps above, a per-worker policy (tools, write scope, network mode, limits, `env_allow`) whose identity is recorded in each audit line, tool-set intersection, audit on our side (who, what, when, exit), output review and export of changes as reviewed patches, and cleanup of everything the job created. The RWP container backend maps to this contract through an adapter **after** its own qualification; a direct executor is never labelled an RWP-conformant workplace.
- *Audit, both sides:* our executor logs who, what, when, policy identity and exit; the donor's bridge logs tool name, argument hash and sizes (never arguments or environment), owned by the bridge identity, so the donor can see what left their machine and the harness cannot edit the record.
- *Signing (F18):* the worker's signing key `K_sig` never leaves the donor's bridge identity. For an outbound message the donor bridge builds the **final** envelope (canonical bytes with the audience and thread declared in the task record it answers; no projection after signing), signs it with `K_sig`, and sends `mailbox.post {envelope_bytes, signature}`. Our bridge verifies the signature against the pinned key, checks grants and freshness (ADM), admits, and carries the bytes **unchanged** into the carrier under its own carrier account for that worker; the carrier authentication is a distinct authority, recorded as such in the schema and the audit, never presented as a worker signature.
- *Delivery (F19):* the orchestrator posts a signed task message to the worker's mailbox (a snapshot of one element; no board access). Our bridge admits it (signature, grant, decision guard, fence) and sends an advisory `mailbox.notify`. The donor bridge pulls `mailbox.read {from_cursor}` and performs its **own admission**: the verification record is present, the target binding is this worker, the message is unexpired and not fenced or revoked, the delivery mode is allowed. An admitted **task turn** is handed to the harness through the supervisor's session-input adapter; ordinary data is readable through the `mailbox_read` tool when the policy grants it. Both sides keep durable high-water cursors; a cursor advances only after the item is persisted; after a reconnect the donor bridge catches up from its cursor and deduplicates by `message_id`; `mailbox.applied {message_id}` is the application receipt, distinct from the transport reply. Pending outbound posts are queued durably on the donor with stable `op_key`s and flushed after reconnect.
- *Disconnected behaviour:* while the SSH channel is down, the project mailbox stays durable and the donor bridge pauses the turn loop (no new turns); a running turn continues until its deadline, its tool calls fail with the retryable `channel_down`, and its result post is queued; after `disconnect_grace` the supervisor parks the session and reports `channel_down` in `status`. Never, in any state, does the donor receive a carrier credential.
- *What the worker sees:* its managed home, the task snapshot, its admitted mailbox view. *What it never sees:* our board, the carrier, carrier credentials, the bridge's keys and state, other homes, the network beyond the proxy.

**D6. MITM, replay and identity (F13).** First contact is protected by the out-of-band pin (the invitation names the root and the SSH host key fingerprints; the human compares the worker fingerprint over a second channel) bound to a one-use random code and a server challenge, by the signed transcript (proof of possession over a challenge, not over a client-chosen nonce), and by the DNSSEC/DANE cross-check where a trusted validator exists. After that everything is pinned: the three worker keys in our registry and `K_ssh` in the root-owned authorized-keys file, our root, operator chain and SSH host key on the donor, operator-signed packages with associated data, and envelopes signed over exact bytes with freshness and replay rules (ADM). Replay of `cert` or `collect` meets the invitation tombstone; replay of a channel frame meets the connection-scoped ids and the `op_key` cache. Compromise of a worker key: the operator revokes with a root-signed record, the authorized key is removed and open sessions are closed (D7). Compromise of our host key: a new key, new SSHFP, and every donor runs `init --rotate-host` against a fresh invitation. Rotation of the operator certificate is a root-signed record the donor fetches at the next connection; a package signed by an expired or revoked operator certificate refuses.

**D7. Lifecycle: stop, leave, purge; suspend, retire, revoke** (`diagrams/remote-worker-retire.puml`; F17). The worker's state is `enrolled → active ⇄ stopped (donor) | suspended (project) → retired → revoked → purged`.
- *Donor side.* `curator remote-worker stop`: persist the stopped mark first, end the harness processes, keep the bridge service and the keys; `status` says stopped; `run` resumes. `curator remote-worker leave`: close the channel, tell our side `retire` if reachable, keep the keys and the configuration, so the same identity can return to a new workplace with a new package (`init --rejoin`). `curator remote-worker purge --confirm`: delete the keys, the locked configuration and the managed home, call the helper to remove both accounts, the egress anchor, the sandbox profile and the daemon unit; print the revocation outcome reported by our side, or "channel unreachable; the project side must revoke separately", because loss of the channel is not evidence of remote revocation.
- *Project side.* `suspend`: grants paused, sessions closed, workplace kept. `retire`: revoke grants and channel authorization, close open sessions, kill every job and its descendants, remove the authorized key, archive only permitted noncredential artifacts, then release the account and firewall state after process absence is verified; the identity stays pinned. `revoke`: a root-signed revocation of `K_sig` (and the other two keys), after which every frame and envelope from that key refuses and a return needs a new key through a new enrolment. A key rotation for a returning worker is a root-authorized record, never silent.
- Ordering: stop and revocation marks are persisted before any service restart can race them; removing an SSH key never substitutes for closing established sessions.

**D8. Donor control surface.** `curator remote-worker status` (posture, tuple, policy generation, project, connection state, last tool call, budget used, audit path), `stop`, `run`, `leave`, `purge`, `audit tail`, and the locked configuration the donor owns. The harness identity cannot change any of it by construction; the operator on our side cannot either.

## Security considerations

- **Boundary on the donor:** two identities, the kernel sandbox with a mandatory read boundary, and the per-UID egress (D1, D2). A compromised harness is confined to its managed home, the scratch dir, the relay socket and the provider proxy; it cannot read the bridge's keys or state, cannot alter the audit, and cannot reach the network. Its provider token is in its environment (CIP-0010, trusted-process posture).
- **Boundary on our host:** the workplace user and the `swarma-workplace-exec/1` policy; the worker can only run what the policy allows, where it allows it; SSH authorization is outside its write authority.
- **Network:** the harness reaches the provider API only through the proxy; the bridge reaches only our hosts; nothing listens on the donor machine.
- **Secrets:** the worker's keys never leave the bridge identity; the provider credential enters the harness per launch (CIP-0010); the carrier credential stays in our bridge; the invitation code is a bootstrap secret with a short life; no secret is in argv or the plan.
- **Supply chain:** the binaries on the donor machine come from the toolchain release with checksums and attestations (R55 discipline), installed into a protected root and verified at every launch; CIP-0007 governs anything else the donor installs.
- **Replay and freshness:** invitation tombstones, server challenges, connection-scoped ids, `op_key` caches, and signed envelopes with `issued_at`, `expires_at` and nonces.
- **Privileged helper:** a closed schema, allocated identifiers, fixed templates, safe path handling (`O_NOFOLLOW`, no symlink following), a journal and rollback; tested against symlink substitution, arbitrary-user removal and argument injection.

- Nothing changes for local launches. The donor-side commands are new. `rwh` becomes the executor behind `swarma-rb-exec` on our host; its `worker` guards move into the bridge service; its Codex single-auth-owner adapter is the Codex node of CIP-0010.

## Test plan

- Handshake negatives: wrong or reused code, expired invitation, wrong challenge, transcript signed by another key, replayed `cert`, `collect` with a different key than `cert`, package signed by a wrong or expired operator certificate, package encrypted to a wrong key, associated data mismatch, bogus DNS result, attempt limit exceeded; a retry with the same key recovers the same enrolment.
- Connection negatives: host key mismatch (pinned vs offered) on first and on later connections, unknown worker key, a workplace shell tool trying to append to the authorized-keys file (not writable), an attempt at port or agent forwarding, a second connection while one is up.
- Protocol negatives: version rejection, truncated and oversized frames, duplicate ids, stale `cancel`, `stdin` to a finished job, caps above policy, `env` outside `env_allow`, unauthorized method, reconnect after an effect (cached result or `unknown_result`, never a replay), descendants after transport loss (none survive).
- Sandbox and provisioning per platform: file reads outside the allow-list refused (including the bridge's home), egress outside the allowlist refused, the proxy refuses a non-provider host, the relay socket refuses another UID, the helper refuses symlink substitution, an arbitrary user in `remove-worker` and an injected argument; provisioning interrupted halfway rolls back; a colliding pre-existing account is untouched.
- Tool set: `tools/list` equals the intersection of the six with the policy; a `tools/call` of another name is an error result and an audit line; a read-only policy offers `read_file` only.
- Signing and delivery: an envelope altered after signing refuses; a valid carrier credential without a worker signature cannot post; a message with a foreign target binding or past its expiry is refused by the donor bridge; cursors survive a restart; a duplicate `message_id` is applied once; `mailbox.applied` is distinct from the transport reply.
- Lifecycle: after `stop` no harness process remains and the bridge is alive; after `leave` the keys remain and `init --rejoin` works; after `purge` no process, key, account or firewall rule remains and the printed revocation outcome matches our side; after `retire` on our side no job, descendant or authorized key remains; after `revoke` a frame from the old key refuses; a stop mark survives a service restart.
